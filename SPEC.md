# Huismus — Specification

> Working name. Check availability (GitHub, .nl/.com, BOIP) before publishing.
> Not accounting or tax advice. Verify legal requirements with the Belastingdienst.

## 1. Purpose

Full bookkeeping for Dutch freelancers (zzp'ers), on their own computer. Decided by the owner on 2026-11-07: Huismus grows from a minimal invoicing tool into a complete bookkeeping package that a large share of Dutch freelancers can use, with or without the **KOR** (kleineondernemersregeling) and with VAT (M18). What is in scope follows from what freelancers use in other packages today and from what keeps them from switching; many features are fine as long as Huismus stays easy to use (principle 7).

**Primary onboarding path: import everything from the package you leave, 1-to-1.** Moneybird first: its complete export imports for any user, to the cent. This is the reason the project exists and the hardest requirement. Rompslomp follows, then other packages and spreadsheets through one documented import format (issue #108). The first users to win over are freelancers leaving Moneybird or Rompslomp; then everyone who keeps their own books.

The books stay local: one installation per administration (desktop app or Docker). What cannot work locally (a live bank connection, a phone app, filing returns directly, payment links, Peppol) is out of scope until a separate decision (issue #64).

### Non-goals

Payroll, multi-tenant hosting, a hosted SaaS version, e-commerce. A live bank connection is out of scope for now (a bank statement file is in, issue #77); so are the other features that need a central server (issue #64).

## 2. Principles

1. **Issued documents are immutable.** Corrections go through credit notes. The one way out is the user's explicit "Toch bewerken" (invariant 1).
2. **Money is integer cents.** Never floats. VAT rates in basis points. Amount fields show and take Dutch notation ("20.000,00"; "12.50" still works), in both languages, like every amount on screen (decision 2026-10-29).
3. **The user owns the data.** One SQLite file plus one `data/` directory. Backup = copy them.
4. **Dutch first, i18n from day one.** All UI strings go through gettext. `nl` is the default language, `en` second.
5. **Import fidelity beats convenience.** Totals must match the source to the cent, or the import reports why.
6. **Local and quiet.** One process (one container, or one desktop app, M11), no external services, no telemetry. Huismus makes only four kinds of outgoing request: the update check (M11; in Docker too since 2026-11-04, only to say so), which can be turned off; backups to the one cloud service the user linked (M15 step 2; decided 2026-10-30), which are off until linked, and through that same Dropbox or WebDAV link the receipts folder (on Dropbox also waiting there for a change), when the user chooses it (M20); "Hoe gebruik je Huismus?" (M13), sent only when the user presses Versturen after seeing everything that goes (decided 2026-11-02); and receipts to the AI service the user chose to read them (M20, part 3; decided by the owner 2026-11-06), which is off until the user sets one up with their own key.
7. **Easy to use.** Replaced "Small" on 2026-11-07: Huismus may do a lot, but every screen stays simple, and what you do not use you do not see (with the KOR on, for example, no VAT fields). The hard rules in `CLAUDE.md` all stay.

## 3. Stack

| Concern | Choice |
|---|---|
| Language | Python 3.12+ |
| Framework | Django (current LTS): auth, ORM, migrations, forms, i18n, file uploads |
| Database | SQLite in WAL mode |
| UI | Django templates + HTMX, plain CSS design system; vanilla ES modules for progressive enhancement only (no SPA, no framework, no JS build step) |
| PDF | WeasyPrint (HTML/CSS → PDF); needs Pango, provided in the Docker image |
| Excel import | openpyxl |
| UBL import | lxml |
| Serving | gunicorn + WhiteNoise |
| Packaging | Docker image for arm64 and amd64 (Raspberry Pi is the reference target); a desktop app for macOS and Windows (M11) |
| Tests | pytest, pytest-django, hypothesis |

Rationale for Django over an API-first framework: this is a server-rendered CRUD app, and Django's built-ins remove the need for custom auth, migration tooling and translation plumbing.

## 4. Data model

All tables have `id`, `created_at`, `updated_at`. Money columns end in `_cents` (BigInteger).

### Settings (singleton)
`business_name`, `legal_form`, `address_line1`, `address_line2`, `postal_code`, `city`, `country`, `kvk_number`, `iban`, `bic`, `email`, `phone`, `website`, `vat_number` (optional), `kor_enabled`, `kor_text` (shown on every invoice when enabled), `kor_limit_cents` (default 2 000 000) and `kor_warning_percent` (1–100, default 80) for the KOR-limit warning (M12), `reverse_charge_text` (under every document with a "verlegd" line, M18; empty by default), `logo` (file in `data/`), `default_payment_terms_days`, `invoice_number_format`, `quote_number_format`, `number_reset_yearly`, `default_footer_text`, `default_language`, `currency` (default `EUR`), and for mailing (M10): `smtp_provider` (empty = mailing off, `gmail`, `other`), `smtp_host`, `smtp_port`, `smtp_security` (`starttls` | `ssl`), `smtp_username`, `smtp_from_email` (empty = `email`), and the mail texts `mail_<kind>_subject_<lang>` and `mail_<kind>_body_<lang>` for kind `invoice`, `credit_note`, `quote` and language `nl`, `en` (empty = the standard text). The SMTP password is not a field of this table: it is kept in its own file, `data/smtp-password` (owner-only), which backups skip.

Changing settings never alters issued documents (see snapshots).

### Contact
`customer_number`, `company_name`, `first_name`, `last_name`, `attention` (the "T.a.v." on its documents; Moneybird's `attention`), address fields, `country`, `email`, `quote_email` (quotes are mailed here when set; Moneybird's `send_estimates_to_email`), `delivery_method` (`email`, `post` or none; the mail page says when a customer wants post), `phone`, `kvk_number`, `vat_number`, `iban`, `payment_terms_days` (override), `notes`, `archived`, `source`, `external_id`.
Unique on (`source`, `external_id`) when set.

### ContactPerson
`contact` FK, `name`, `email`, `phone`, `department`.

### Document
One table for quotes, invoices and credit notes.

- `kind`: `quote` | `invoice` | `credit_note`
- `status`: quotes: `draft`, `sent`, `accepted`, `declined`, `expired`; invoices and credit notes: `draft`, `issued`
- `number` (null while draft), `issue_date`, `due_date`, `delivery_date`
- `contact` FK (nullable after archive), `contact_snapshot` (JSON), `business_snapshot` (JSON), `kor_text_snapshot`, `reverse_charge_text_snapshot` (M18)
- `accepted_on`, `declined_on` (quotes): the day of the answer, set by accepting or declining, or imported from Moneybird's `geaccepteerd op` / `afgewezen op`; shown in the quote's timeline
- `reference`: the "Kenmerk" (Moneybird's `referentie`), under the title on the PDF
- `attention`: the "T.a.v." line, a name chosen in the editor from the contact's own `attention` and its contact persons (as in Moneybird; `huismus-intern/besluiten.md` 2026-10-30). Part of the document, so immutable once issued
- `language`, `currency`
- `intro_text`, `footer_text`, `notes`
- `subtotal_cents`, `tax_cents`, `total_cents` (computed at issue, stored)
- `related_document` FK (invoice → originating quote; credit note → credited invoice)
- `reopened_at` (set by "Toch bewerken", see invariant 1)
- `before_reopening` (JSON, while reopened: the document as it was issued, so "Annuleren" can restore it; see invariant 1)
- `source`, `external_id`

### DocumentLine
`document` FK, `position`, `description`, `quantity` (Decimal, 3 dp, optional: empty = fixed price, counts as 1), `unit`, `unit_price_cents`, `tax_rate_bp` (0 for KOR; which rates a line may have: `huismus/documents/vat.py`, invariant 6), `reverse_charge` ("verlegd": the line has 0% and the PDF says so, M18), `line_total_cents`.

### DocumentVatRow
`document` FK, `rate_bp`, `reverse_charge`, `revenue_cents`, `tax_cents`: the revenue (without VAT) and VAT of one rate on an issued invoice or credit note, reverse charge apart, as on its PDF (M21). Stored once, when the document is issued, from the one totals function (invariant 3); positive on a credit note, like its totals. Immutable like the lines (invariant 1). None for an import whose stated totals are not those of its lines.

### Payment
`document` FK, `paid_on`, `amount_cents`, `method`, `note`. Payment state (unpaid, partial, paid, credited) is derived, not stored: an invoice is settled by its payments plus the issued credit notes against it; "credited" when the credit notes alone cover the total. Outstanding = invoice total − issued credit notes − payments.

### Attachment
`document` or `expense` FK, `file`, `kind` (`original_pdf`, `receipt`, `other`), `sha256`, `source`. Never both. Neither only for a receipt waiting for an expense, fetched from the receipts folder (`source` `bonnetjesmap`, M20).

### Expense
`date`, `supplier`, `description`, `amount_cents` (**gross amount paid**, always stored gross: invariant 7 of CLAUDE.md), `vat_info_cents` (under the KOR informational; with the KOR off the input VAT, decided by the owner 2026-11-06, not built yet: issue "Voorbelasting op uitgaven"), `source`, `external_id`. Has lines, as in Moneybird (decided 2026-11-02, `huismus-intern/besluiten.md`): `amount_cents` and `vat_info_cents` are the sums of its lines, stored by one function (`huismus/expenses/lines.py`).

### ExpenseLine
`expense` FK, `position`, `description`, `amount_cents` (gross), `vat_info_cents` (informational; optional with the KOR on, required without it, where € 0,00 is a valid answer: decided by the owner 2026-11-05; the amount stays gross; with the KOR off this is the input VAT once that is built), `vat_rate` (21, 9, 0 or one of three kinds of reverse charge; required without the KOR, empty = never counted as input VAT; M21), `category` FK (optional). The year overview's per-category breakdown and the list's category filter work per line. Existing expenses got one line each with their amount, VAT and category (migration `expenses.0002`).

### ExpenseCategory
`name`, `sort_order`.

### NumberSequence
`kind`, `year` (nullable), `last_value`. Allocated at issue time, inside the same transaction as the status change.

### EmailLog (append-only)
`document` FK, `sent_at`, `to`, `bcc`, `subject`, `body`, `attachment_name`, `attachment_sha256`, `succeeded`, `error`. One row per attempt to mail a document (M10), successful or not. Never updated or deleted.

### ImportRun
`source`, `started_at`, `dry_run`, `file_hashes` (JSON), `report` (JSON), `committed`.

### AuditLog (append-only)
`at`, `event` (`document_issued`, `credit_created`, `settings_changed`, `import_committed`, …), `object_ref`, `detail` (JSON).

## 5. Invariants (enforced in code AND covered by tests)

1. **Immutability.** Once a document is `issued`, neither the document nor its lines can be updated or deleted. Enforced in model `save()`/`delete()` and by SQLite triggers (`RAISE(ABORT)`) as defense in depth. The same holds for its VAT per rate (`DocumentVatRow`, M21).
   One exception, decided on 2026-10-18: **"Toch bewerken"**. On an issued invoice or credit note the user may choose, after a warning that a credit note is the usual correction, to turn it back into a draft (`huismus/documents/reopening.py`). It keeps its number, issue date, business and KOR snapshots and VAT rates; issuing it again takes no new number and a fresh contact snapshot. The trigger lets exactly that change through (status `issued` → `draft`, same number, new `reopened_at`); every other change to an issued row is still refused. Refused when an issued credit note exists against the invoice (invariant 5). A draft invoice or credit note that has a number can never be deleted (invariant 2), in the model and by trigger. The page shows that the document was reopened; for an imported one the re-rendered PDF becomes the primary one.
   Added 2026-10-22: the warning says what already happened (when and to whom it was mailed, what was paid), and after issuing again the page says the customer still has the old version until it is mailed again. Reopening keeps a copy of the issued document (`before_reopening`): "Annuleren" in its editor restores exactly that and makes it issued again, with the same number, snapshots and totals, discarding what was changed since. Issuing it again drops the copy.
2. **Gap-free numbering.** Numbers are assigned only when issuing, in a transaction that holds the sequence row. A test issues documents concurrently and asserts no gaps and no duplicates.
3. **One totals function.** `total = Σ line totals + tax`. Line total = quantity × unit price (an empty quantity counts as 1), rounded half-up to cents. Tax is calculated per document per rate group, not per line (matches Dutch practice and Moneybird's own behaviour). All code paths use this one function; hypothesis tests cover it.
4. **Snapshots.** On issue, store business, contact, KOR text and reverse charge text snapshots. Later edits to settings or contacts never change existing documents.
   One exception: the logo. A document whose snapshot has no logo (imported, or issued before a logo was set) is rendered with the current logo. The logo is branding, not content; no text, amount or address is ever taken from live settings. A snapshot that has a logo always keeps it.
5. **Credit notes.** A credit note references an issued invoice; the sum of credits for an invoice never exceeds its total.
6. **KOR guard.** If `kor_enabled`, issuing requires non-empty `kor_text`, and new invoices and quotes created in the UI use 0% tax; a credit note keeps the rates of the invoice it credits (it corrects that invoice, it is not a new one), and a reopened document (issued before, maybe before the KOR) is not under this guard: it offers 0, 9 and 21% plus its own rates. Imported invoices with tax > 0 must still import and render faithfully. With the KOR off, a line has 0, 9 or 21% (M18). One module decides the rates for the editor, issuing and the AI connection: `huismus/documents/vat.py`.
7. **Imported issued documents are immutable too** (with the same "Toch bewerken" exception, invariant 1) and keep `source` and `external_id`.

### M10 — Mailing documents
Huismus mails an issued invoice, an issued credit note or a quote that has been sent (any status with a PDF) itself, over SMTP with Django's built-in `django.core.mail` (no new dependency).
- **One SMTP configuration** in the settings screen, with a preset "Gmail" (`smtp.gmail.com`, port 587, STARTTLS, an app password) and "Anders" (host, port, STARTTLS or SSL, username) for a mail server of one's own. The sender is `smtp_from_email`, or the business e-mail when empty. The password is typed in the same screen and kept in its own file `data/smtp-password`, outside the database, which backups skip (decided 2026-10-22, replacing the environment variable `HUISMUS_SMTP_PASSWORD` of 2026-10-21: setting it there needed a container restart; the reason stays that a password in the database would end up in every backup). The screen shows whether it is set, never its value; an empty field keeps it, "Niet ingesteld" removes it. A Gmail app password is saved without the spaces Google shows. A "test mail" button mails the sender address.
- **Mail texts** (added 2026-10-22) in the same screen: a subject and a body per kind of document (invoice, credit note, quote) and per language (Dutch, English), prefilled with the standard text. Placeholders: `{nummer}`, `{bedrag}`, `{naam}`, `{bedrijf}`, plus `{vervaldatum}` for an invoice and `{geldig_tot}` for a quote; any other `{…}` is refused when saving. A line with a date placeholder whose date is missing is left out. An empty text means the standard text. The text only fills the mail form; the mail log keeps what was actually sent.
- **"Mailen" button** on those documents, opening a form with: recipients (default: the contact's current e-mail address; several separated by commas), subject and body (prefilled with the mail text for that kind of document in the document's language, editable per mail), and "BCC to myself". The PDF goes along as attachment, named after the number; for an imported invoice that is its original PDF when there is one (section 7: the original PDF is the legal record) and it was not edited in Huismus since ("Toch bewerken"), otherwise the PDF from the snapshots.
- **Every attempt is logged** in `EmailLog`, with the error when it failed (never the password), and shown on the document's timeline: the invoice timeline gains mails, and credit notes and quotes get a timeline of their own (created, issued or sent, mails).
- **Mailing changes nothing about the document**: no status, snapshot, number or total (invariants 1 and 4). A draft quote is sent first, then mailed: two steps.
- Sending happens in the request, with a timeout; there is no queue (principle 6). Tests use Django's locmem mail backend and never send real mail.
- Out of scope: recurring invoices, payment reminders, AI/MCP access, retrying in the background, configurable default texts.
*Done when:* mailing works against a real SMTP server from the running container, tests cover the log, the attachment and the untouched document, there is an e2e test for the button, strings exist in Dutch and English, and `docs/hulp/mailen.*.md` explains both setups, including how to make a Gmail app password (M17).

### M11 — Desktop app (macOS and Windows)
Beside the Docker/Pi route, not replacing it: Huismus as an ordinary desktop app for a freelancer without technical knowledge. Download, double-click, and a window opens; no Docker, no terminal, nothing to configure. It is the same Django app with the same SQLite database and the same invariants; only the packaging and the first start differ. Decided on 2026-10-27 (advice: "Huismus installeren zonder gedoe").
- **Packaging.** Python, the dependencies and Pango (for WeasyPrint) go inside one app per platform: a `.dmg` for macOS and an installer `.exe` for Windows. At start the app runs the migrations, starts the Django server on `127.0.0.1` on a free port, and shows it in a native window (the system's webview: WKWebView on macOS, WebView2 on Windows). Closing the window stops the server; nothing keeps running in the background. The packager and the window library are chosen at the start of the milestone (section 13). The shell is Python, so the CLAUDE.md conventions (no JS framework, no build step) hold. The shell starts Django with a desktop setting (`HUISMUS_DESKTOP=true`); Docker never sets it, so everything below that is desktop-only stays off there.
- **Zero configuration.** Without a `SECRET_KEY` in the environment, Huismus creates one on first start and keeps it in an owner-only file in `data/`, left out of backups like the SMTP password. A `SECRET_KEY` from the environment takes precedence. This applies to Docker as well, so a first `docker run` needs no key either; it replaces the deliberate refusal in `huismus/config/settings.py` and `tests/core/test_settings.py`, and CLAUDE.md is updated in the same change. Because the key is not in a backup, restoring on another computer means signing in again; no data is lost. On the desktop, hosts are fixed to `127.0.0.1`/`localhost` and the login cookie does not require HTTPS. The data directory is the system's own place: `~/Library/Application Support/Huismus` on macOS, `%APPDATA%\Huismus` on Windows.
- **Login is optional on the desktop, off by default.** The laptop's own lock protects it; whoever wants a password sets one in Settings. Without a login, the server only accepts requests carrying a random token that the app hands its own window at every start, so a browser tab or another program on the same computer cannot use it. The window's first request trades the token for a cookie, so forms, CSRF and HTMX work as they do now. The token stays required when a password is set. On Docker/Pi a login stays required. Built 2026-10-29 (design D6; choices: `huismus-intern/besluiten.md`): Instellingen → Wachtwoord sets, changes or turns off the password; changing and turning off need the current one, and wrong guesses count towards the login limit. With a password the app's login page asks only the password, at every start.
- **First start is the onboarding**: business details, then importing the Moneybird export (section 1) or skipping it, then the dashboard with its checklist (M8). Setting a password is offered there too: the done page of the step-by-step start (M13) links to Wachtwoord, in the desktop app only.
- **Not signed** (decided 2026-10-27: a hobby project). No Apple Developer ID and no Windows certificate; the macOS app carries only a free ad-hoc signature, without which it will not start on Apple Silicon. The download page explains, with screenshots in Dutch and English, the one-time step on first opening: on macOS System Settings → Privacy & Security → "Open Anyway" (the step links straight to that screen), on Windows "More info" → "Run anyway". Signing can be added to `release.yml` later without changing the app.
- **Updates.** The app checks GitHub Releases for a new version, downloads it in the background and installs it by itself the next time it opens, before the user can work (the owner's decision, 2026-11-04; `huismus-intern/besluiten.md`); a button in Settings → Updates updates right away, and "Nu zoeken" there looks for a new version right away instead of waiting for the daily look (on Docker too; the owner's request, 2026-11-05). ### M15 — Backups on every installation
Decided on 2026-10-30 (`huismus-intern/besluiten.md`): Huismus works the same on every installation (desktop app, Pi, NAS, any Docker server), so the desktop app's backups (M11) come to the Docker version too, and backups can go straight to a cloud service. Two steps.

A folder that is not on a linked disk is refused, since it disappears when the container is replaced. A new database and the sample data get no backup (`huismus-intern/besluiten.md`, 2026-11-04).
- **Step 2: Dropbox and WebDAV** (built 2026-10-31; Google Drive and OneDrive follow as their own step, `huismus-intern/backlog.md`). ### M16 — AI connection (MCP)
Decided on 2026-10-28 and 2026-10-29; build choices by the product-owner agent on 2026-10-30 (`huismus-intern/besluiten.md`, "AI-koppeling (M16 stap 1): bouwkeuzes"). An AI assistant (the Claude app, Claude Code, ChatGPT, Gemini CLI) works with the administration through the Model Context Protocol. - **Step 1: an address with a key, everywhere.** `/mcp` speaks MCP over "Streamable HTTP" (stateless, JSON answers, no event stream), built on Django without the `mcp` package (that is an ASGI stack; Huismus is WSGI). It answers only requests with `Authorization: Bearer <key>`, never a session cookie, and refuses an `Origin` of another host. The key lives in its own owner-only file in `data/`, left out of backups (section 9). Without a key `/mcp` refuses everything. In the desktop app the window token does not apply to `/mcp`; the key does, and the app tries port 8765 first so the address stays the same.
- **What the assistant may do.** Read: an overview (revenue this year against the KOR limit, outstanding, overdue), searching and opening invoices, credit notes and quotes, searching contacts, expenses per year, and the receipts without an expense (M20, part 2); no settings, other attachments, PDFs, mail texts or mail log. Confirm: issuing an invoice or credit note, sending a quote and mailing a document are separate actions, marked destructive and never read-only, so the assistant's app asks the user before each; a read action before each gives the summary (customer, amount, the number it will get, and the KOR-limit line of the issue dialog, M12). Mailing goes only to the customer's address with the standard subject and text. Expenses (besluit 2026-11-02, `huismus-intern/besluiten.md`, "AI-koppeling: uitgaven toevoegen"): `add_expense` adds one with its lines (gross amount, optional VAT for information, an existing category by name or none), through the expense page's own forms and `huismus/expenses/lines.py`; not destructive, since it gets no number and the user can change or delete it; no categories made; a receipt only from the receipts without an expense (M20, part 2), else the answer says to add one in Huismus, with the path to the expense. Only in the desktop app, the page shows a card **Claude** first: one line, the pill and a button **Koppel met Claude**, a plain POST. The Moneybird import takes 21, 9 and 0 when Moneybird's rate name says exactly that, and its "Binnen EU 21% (btw verlegd)" and "Buiten EU 21% (btw verlegd)" as reverse charge in another EU country and outside the EU; any other rate (an old 6%, or a rate without a name) stays empty and the dry run names it ("Btw-tarief onbekend"); an export without rate columns gives no message. Existing expenses keep no rate: none is guessed. A line without a rate never counts as input VAT.
- **Part 3, input VAT** (product-owner agent 2026-11-07, `huismus-intern/besluiten.md`, "Voorbelasting op uitgaven: wanneer, verlegd, weergave en label"). With the KOR off, the year overview reads the costs per expense line (`huismus/reports/year_overview.py`): at 21, 9 or 0% costs = gross − VAT and the VAT is input VAT; reverse charged or without a rate, costs = gross. Its card "Kosten zonder btw" with "Voorbelasting € …" under it, a column "Voorbelasting" per quarter, "Kosten zonder btw per categorie", the CSV (columns "kosten zonder btw" and "voorbelasting"), the overview's "Kosten zonder btw" and the AI connection's `list_expenses` (`total`, `total_without_vat`, `input_vat`) follow; profit = revenue − costs without VAT. With the KOR on everything stays gross, as before, also for past years. Nothing stored changes (hard rule 7). The export's `uitgaveregels.csv` gets "btw-tarief" (the name as on the page) and calls the VAT column "btw" without the KOR, "btw ter info" with it; `uitgaven.csv` stays gross. Later: after turning the KOR off, past KOR years show input VAT for imported lines that have a rate; such a rate can be emptied on the expense.
- **Part 4, the VAT return** (product-owner agent 2026-11-07, `huismus-intern/besluiten.md`, "Btw-aangifterapport: plek, periode, opbouw en wat niet meetelt"; which box holds what: the owner, escalation list 1). Rapporten → Btw-aangifte (`/rapporten/btw-aangifte/`, `huismus/reports/vat_return.py`), with tabs "Jaaroverzicht | Btw-aangifte" above both reports; the menu still opens the year overview. A period is a quarter, month or year (`?periode=2026-Q3`, `2026-07`, `2026`, `huismus/reports/periods.py`); by default and for anything unknown or not yet begun, the last finished quarter; no step beyond the current one. It only reads. Sales: the stored rows (part 1) of invoices and credit notes with status issued and an invoice date in the period, a credit note negative: 21% → 1a, 9% → 1b, 0% → 1e, reverse charged by the country in the customer snapshot: Netherlands → 1e, another EU country → 3b, which counts in the period of the delivery date when the document has one and else of the invoice date, so it can come from a document invoiced in another period (issue #113) (EU list and box titles in `docs/belastingregels.md`, "Rubrieken in detail"). Purchases: expense lines by their expense's date: "Btw verlegd: Nederland" → 2a, "buiten de EU" → 4a, "ander EU-land" → 4b, each with the amount as value and the VAT the user entered; 5b is the VAT of lines at 21, 9 or 0% plus that reverse charged VAT ("waarvan verlegd"). 5a is the VAT of boxes 1 to 4; then "Te betalen" or "Terug te krijgen". Amounts in cents, not rounded. Box titles word for word from the Belastingdienst's explanation. Under "Niet meegeteld", with a warning at the top and a link per item: issued documents without rows (Moneybird's amounts), rows at another rate (6% before 2019), reverse charged to a customer outside the EU or without a country, documents with the KOR text, documents back in draft through "Toch bewerken", and expense lines without a rate or VAT. With the KOR on, the page shows only a notice with a link to the KOR settings and no figures (the owner, 2026-11-07): under the KOR the VAT on expenses counts nowhere (hard rule 7), and no expense line is read. The CSV and the AI connection: part 5.
- **Part 5, the VAT return as CSV and for the AI connection** (issue #112; product-owner agent 2026-11-07, `huismus-intern/besluiten.md`, "Btw-aangifterapport: CSV en AI-koppeling"). ## 7. Moneybird import (M5)

### What Moneybird exports (as documented by Moneybird)
**Everything goes along** (decided 2026-11-01, `huismus-intern/besluiten.md`): every part of the Moneybird administration that Huismus has a place for is imported, not just part of it.

Moneybird gives one **year export** (jaarexport) per financial year: a ZIP named after the administration and the year (Instellingen › Boekhouding › Boekhouding exporteren › "Download jaarexport"; without a subscription: "Exporteren" › "Alle gegevens", one ZIP per year). Inside: a folder per part and a `LEESMIJ.txt` listing them. Contacts, products and recurring invoices are in every year's export, as they are at that moment. The user drops all years' ZIPs at once. Separate exports of a single part (contacts, invoices, quotes) are accepted too. The parts:

- **Contacts** (`contacts/`): Excel with sheets `Contacten` and `Contactpersonen`, linked by customer number.
- **Sales invoices** (`sales_invoices/`, `sales_invoices_details/`, `sales_invoices_archive/`, `sales_invoices_ubl_archive/`): Excel per invoice, Excel per line, the PDFs, the UBL files (sent invoices only). Attachments are not included. Per-line exports do not always show VAT per line, so the per-invoice export is the source of truth for totals.
- **Quotes** (`estimates/`, `estimates_details/`, `estimates_archive/`).
- **External sales invoices** ("Externe verkoopfacturen export", "Externe verkoopfactuurregels export", "Externe verkoopfacturen archief"): invoices made outside Moneybird and only registered there. They count as revenue, so they go along too (decided 2026-11-01). Not built yet (`huismus-intern/backlog.md`).
- **Incoming documents / purchase invoices** (`documents/`, `documents_details/`, `documents_archive/`): become **Expenses**, with their files as receipts, gross amounts (invariant 7). Required, not optional. The columns come from the anonymised 2013 and 2014 sample exports, never from guesses (invariant 6). Purchase invoices are on the sheet `inkoop`; another sheet of incoming documents with the same columns is named in the report and not imported.
- **Not exportable**: periodic (recurring) invoices. Moneybird exports the schedule only. The import report must say so.
- **Not in scope now, maybe later**: products, projects (revenue and costs per project), hours (Uren), rides (Ritten), bank transactions and the bank link (decided 2026-11-01). The bookkeeping reports in the export (balance, ledger accounts, VAT overview, ageing) are derived from the records above, so they are not imported either; two of them serve as a cross-check (below).

### Input handling
- Accept the **raw, unmodified** Moneybird files. The user should not edit or convert anything.
- Detect file type by **sheet names and column headers**, never by file name.
- Header alias tables per format variant. Unknown columns produce warnings, not crashes. Missing required columns produce a clear, translated error naming the column.
- **Nothing is lost without a word** (decided 2026-11-02, `huismus-intern/besluiten.md`, "Moneybird-import verliest nooit stil gegevens"; texts by the PO agent the same day). Every column of every sheet the import reads has a destination in `huismus/imports/columns.py`: read (some required), deliberately left out with the reason, or unknown. An unknown column, and a sheet Huismus doesn't know (not a part it reads, nor one of the reports, products or bank transactions it leaves out), are named in the report once per file; the import goes on. A sales invoice or quote whose `valuta` is not EUR stops the import (Huismus stores euros only); expenses keep using the "(EUR)" columns. A `totale korting` other than 0 is named per document under "Korting" (Moneybird's total is kept; the lines show no discount), and not also as a discrepancy. Every report section shows how many documents the export had, and new + already present + skipped add up to it; if they don't, the import stops and saves nothing. Lines whose document isn't in the export are named by row, with the export they are in.
- **The export is kept.** A real import (never a dry run) stores every row of the sheets it reads, their line sheets and unknown sheets, cell for cell (`ImportedRow`), and the original export as given in `data/import-archief/`, which goes into every backup. The same row or file is kept once, however often it is imported.
- Entry points: a web page (upload several files at once) and a CLI (`manage.py import_moneybird <dir>`).
- Several exports in one run: Moneybird exports one year at a time (each with only that year's documents and the full contact list of the moment). Every archive is one export, recognised by its content even without a `.zip` name; loose files together are one more. Each export is parsed on its own, then combined: identical copies of a contact or document count once; copies that differ come from the last export by name (the newest year), and the report says so. Original PDFs are matched per export by `external_id`, since numbers can repeat across years. One export holding more than one file of a kind (beyond Moneybird's own `_archive` copy), e.g. two unzipped years side by side, fails with a clear error instead of picking one.

### First task of M5
Collect **anonymised sample exports** (contacts, invoices per invoice/per line, UBL, quotes, purchase invoices) from at least two different Moneybird administrations, and commit them as fixtures under `tests/fixtures/moneybird/`. Real column names come from these files, not from assumptions. Contributors can add fixtures for new variants.

### Pipeline
1. **Parse** each file into normalised intermediate dataclasses.
2. **Link**: lines to invoices, contact persons to contacts, PDFs to invoices by invoice number.
3. **Validate**: recomputed totals equal stated totals, per invoice, to the cent; number sequence checked for gaps and duplicates; duplicate contacts flagged.
4. **Dry-run report** (default): counts of new/unchanged/skipped, every discrepancy listed, nothing written.
5. **Commit** in a single transaction; store an `ImportRun`.

### Properties
- **Idempotent:** keyed on (`source`, `external_id`), falling back to invoice number. Re-importing changes nothing.
- **Faithful:** imported invoices are stored as `issued` with their original numbers, dates, lines, and payment state where present in the export. Except invoices that were never sent: Moneybird's `status` `draft` and `scheduled` (ingepland) become drafts that keep their Moneybird number, if any, and get no snapshots, payment or original PDF; the report lists them. An unknown `status` fails the import clearly. (Mapping: `huismus/imports/invoices.py`, from the states in Moneybird's API documentation.)
- **The customer as on the document.** An imported invoice or quote's contact snapshot takes the customer's name, address, e-mail, phone, VAT and KvK number from the document's own row in the export (as they were then), on top of the contact as it is now. A line keeps the unit of Moneybird's `aantal` ("2,5 uur" → unit "uur"; "x" is no unit). Only for documents imported from now on: a re-import never changes an imported document.
- **Original PDF is the legal record.** When a PDF ZIP is provided, attach the matching PDF as `original_pdf`; the UI shows it as the primary document for imported invoices. A re-rendered PDF is offered separately and labelled as such.
- **Numbering continues.** After import, the sequence continues after the highest imported number, using the configured number format. A format holds `{year}`, `{seq}` and `{customer}` (the contact's customer number), so Moneybird's default numbering (`{customer}{seq:04d}`: customer 58, sequence 97 is `580097`, one sequence across all customers) continues unchanged. Issuing refuses a contact without a customer number when the format needs one, and a number that already exists; either refusal leaves no gap. If existing numbers cannot be parsed against the format, the user sets the next number manually.
- **Settings from the export.** The web dry run proposes settings from the export itself, for the user to check instead of type: business details from the UBL of the newest invoice (a business moves and changes accounts over the years), the most common payment term, and Moneybird's number format `{customer}{seq:04d}` when every invoice and quote number follows it. The dry run applies the proposal inside its rolled-back transaction, so its report shows the result (numbering continuing); "commit" validates what the user confirmed like the settings page does, and saves it in the import's own transaction, before importing. Where a current setting differs, the dry run shows it. The CLI leaves Settings alone.
- **UBL as a cross-check, and the source of the lines** (decided 2026-11-02, `huismus-intern/besluiten.md`, "Moneybird-import: de UBL als tweede bron voor de regels" and its confirmation). A sent invoice's UBL (`sales_invoices_ubl_archive/<number>.xml`, same export) *fits* when its number, date, subtotal, VAT and total equal the invoice export's, it has as many lines as the line export, and no line has a discount of its own. Then Huismus takes each line's description, quantity, price without VAT and VAT rate from the UBL, and the unit from the line export in the same order; this always applies, also where the Excel lines add up. Where prices included VAT in Moneybird, the Excel line export gives the price with VAT and the UBL without, so this is what puts the right prices on those invoices. The totals stay Moneybird's own from the invoice export and are checked to the cent as before. Compared, `_x000D_` in Excel counts as a line break. A discount on the whole invoice in the UBL (an `AllowanceCharge`, or `AllowanceTotalAmount` not 0) puts the invoice under "Korting", lines at the price before discount, as for a discount in the Excel export. In the dry run, under "UBL-bestanden" in the invoices block (only when the export has UBL files): a UBL that doesn't fit (which fields; the Excel lines stay), a line of a fitting UBL that differs in more than a price including VAT (which fields; the UBL lines are taken), and an invoice already in Huismus whose lines differ from its UBL (it isn't changed; "Toch bewerken" is the way to fix it). These count as points to check and stop nothing. How many invoices had prices including VAT is always said; when nothing is reported, one line says the UBL files match. A UBL that can't be read (broken XML, another root element than `Invoice`, no number) and a UBL without an invoice in the export are named under "Let op". Reading and comparing: `huismus/imports/ubl.py`.
- **Moneybird's own reports as a cross-check** (decided 2026-11-02, `huismus-intern/besluiten.md`, "Moneybird-import: controle tegen Moneybirds omzetrapport" and its addition on the tolerance). Per export, the dry run compares the invoices as Huismus has them after importing (issued, of that export, including ones already there) with two reports in the same export: revenue per contact per month (`RevenueByContact`: the contact's current name, revenue excluding VAT by invoice date) and the year's sales invoice revenue and VAT in the VAT overview (`Tax Overview`, all rates together). Moneybird rounds these reports per line, differently from its invoices, so a difference of at most one cent per invoice line of Huismus in that cell (or that year) counts as equal; where Huismus has no invoice every cent counts. A difference is listed under "Moneybirds eigen rapporten" in the invoices block and counts as a point to check; it never stops the import, since every invoice is already checked to the cent against the invoice export. When everything matches, one line says so; without either report nothing is shown. A report in a layout Huismus doesn't know is named under "Let op" and not compared. Not compared: the debtor report (its meaning can't be derived from the export), the purchase side of the VAT overview, the split per rate and Moneybird's own "Totaal" row. Reading: `huismus/imports/reports.py`; comparing: `huismus/imports/report_check.py`.
- **Expenses** (decided 2026-11-01, `huismus-intern/besluiten.md`, "Uitgaven uit de Moneybird-import"): every incoming document, whatever its Moneybird status, becomes one Expense: its date, the contact's name as supplier, the supplier's reference (`referentie`) as description, and its lines with their own description and category (Moneybird's `categorie`, found by name or created at the bottom of the list; decided 2026-11-02, replacing "no category"). The amount is the total including VAT from the "(EUR)" column, split over the lines by their subtotal (half-up, the rounding cent on the last line, so the lines add up to exactly what was paid); a line's VAT for information is what its gross adds to its subtotal (none for a foreign currency). A document without lines gets one line with the whole total. Its PDF and image files in `documents_archive/<year>/<kind>/<id>-<referentie>-<contact>/` become receipts, on a commit only; the supplier's UBL file next to them is not attached. Checked to the cent: the lines add up to the subtotal, and subtotal plus VAT is the total; a difference is reported and the expense imported with Moneybird's total. The VAT is not recomputed (it comes from the receipt and is often a cent off). The report lists documents without a receipt. Keyed on (`source`, `external_id`); a re-import skips an existing expense.
- **Quote statuses** (decided 2026-11-01, `huismus-intern/besluiten.md`): `accepted` → accepted, `rejected` → declined, `late` → expired, `billed` (an invoice was made from it) → accepted, keeping "geaccepteerd op" if set; `archived` → accepted or declined by its "geaccepteerd op" / "afgewezen op", otherwise expired. Any other status fails the import clearly.

- A second import run reports zero changes.
- A dry-run leaves the database byte-identical.
- Fixture-based tests cover each supported export variant.

## 9. Security and deployment

- Single user, Django auth, strong password hashing, CSRF on, secure cookies when served over HTTPS. On the desktop (M11) the login is optional and the server only answers its own window.
- Failed logins are capped: after 10 within 15 minutes, every login is refused until those 15 minutes have passed (`huismus/core/login_throttle.py`).
- `SECRET_KEY` and allowed hosts from environment; without a `SECRET_KEY`, one is created in an owner-only file in `data/` and left out of backups (M11). The SMTP password (M10) in its own owner-only file in `data/`, left out of backups. The AI connection's key (M16) likewise. No secrets in the repo or the database.
- Intended for LAN or VPN (for example Tailscale). Document a reverse proxy with TLS. Do **not** recommend exposing it directly.
- Uploads validated by type and size; logo SVG sanitised or rasterised.
- The installable app (M9) caches only its offline page; every page with data comes from the server.
- Backups: a daily backup to a folder on another device, or encrypted to Dropbox or WebDAV, on every installation (M15; `docs/backups.md`; decided 2026-10-30 and 2026-10-31, `huismus-intern/besluiten.md`); SD-card wear; SSD boot option.
